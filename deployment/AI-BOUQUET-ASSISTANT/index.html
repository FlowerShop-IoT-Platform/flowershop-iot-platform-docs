AI Florist — deployment, costs, testing & validation (EP-28 / EP-M10)

Scope: what has to change in production to run the AI Florist as an in-app pilot, how to switch on (and later self-host) the image model, what it costs, and how to test and validate it. Design: docs/superpowers/specs/2026-10-13-ai-bouquet-assistant-design.md. Cost research: docs/superpowers/plans/2026-10-13-ai-bouquet-assistant-costs.md. Date: 2026-10-14. The vendor app is not live; this is a testing prototype.

2. Fly.io resources

2.1 Required for the pilot: keep one API machine awake

The worker runs inside the API process. Today fly.toml uses auto_stop_machines = 'suspend' and min_machines_running = 0, so the machine sleeps when there is no HTTP traffic — a queued job would then stall until the next request wakes the machine (the app polls, so in practice it usually wakes, but a vendor who closes the app mid-job leaves it frozen, and lease/retention sweeps stop).

Change fly.toml [http_service]:

  auto_stop_machines = 'off'      # was 'suspend' — the design-job worker lives in this process
  auto_start_machines = true
  min_machines_running = 1        # was 0

Side effect (positive): MQTT ingest, outbox dispatch, reservation expiry and payment reconciliation also stop pausing.

Resource Change Approx. monthly cost*
API machine shared-cpu-1x, 1 GB, fra from scale-to-zero to always-on ≈ $5–7 (full-month price of the machine you already have; check Billing → Usage for the real delta)
Memory keep 1 GB. Photo processing is bounded (≤ 20 MP decode, one photo at a time per request, ≤ 2 concurrent jobs). Raise to 2 GB only if fly logs shows OOM kills +≈ $5 if needed
Fly Postgres no change; 3 small tables $0
GPU none — Fly has deprecated GPUs; no local inference $0

* Fly prices change by region; treat as an estimate and read the invoice after the first month.

2.2 Later (not needed for the pilot): separate worker

When the API should scale to zero again, run the worker as its own always-on machine and disable it in the API: the queue already supports several workers (SKIP LOCKED + leases). Plan: a FlowerShop.DesignWorker host (follow-up T-28-022) deployed as a second Fly app or process group with BouquetDesign__Worker__Enabled=true, while the API sets BouquetDesign__Worker__Enabled=false. Cost: one more shared-cpu-1x 512 MB–1 GB machine (≈ $3–6/month).

2.3 Cloudflare R2 — private bucket

Manual prerequisite: Fly deployments and database migrations do not create this bucket or its credentials. Create it in Cloudflare before testing stock-photo uploads. Stock photos and AI Florist media use this private store; deploying the application alone is not enough.

  1. Cloudflare → R2 → Create bucket flowershop-design-private, location EU (same account as flowershop-bouquets). Do not connect a custom domain and leave Public access disabled.
  2. R2 → Manage API tokens → Create token: permission Object Read & Write, scoped to only flowershop-design-private. Copy the Access Key ID / Secret.
  3. appsettings.Production.json already points BouquetDesign:Storage at this bucket and the account endpoint; only the keys are secrets.

Set BouquetDesign__Storage__AccessKeyId and BouquetDesign__Storage__SecretAccessKey on the Fly app flower-shop-backend-core as shown below. Keep this bucket private; do not substitute the public bouquet bucket or attach a public domain.

Verify setup through Stock → item → Photos & appearance → Add photo. Reload the item and check that the photo still displays. Uploads do not require an OpenAI key; OpenAI recognition and generation require separate provider configuration. On 2026-10-18, stock uploads returned HTTP 500 before the bucket and credentials were provisioned, then persisted and displayed successfully after setup.

Cost: R2 free tier covers 10 GB storage + 1 M writes + 10 M reads/month. A pilot stores ~5 × 300 KB photos per session (purged after 7 days) plus ~150 KB per preview — well inside the free tier.

2.4 Secrets and config

APP=flower-shop-backend-core

# Required — private media
fly secrets set --app $APP \
  BouquetDesign__Storage__AccessKeyId='<r2 key id>' \
  BouquetDesign__Storage__SecretAccessKey='<r2 secret>'

# Optional — paid providers (leave unset to stay on the free providers)
fly secrets set --app $APP \
  BouquetDesign__OpenAI__ApiKey='sk-…' \
  BouquetDesign__Recognition__Provider=OpenAI \
  BouquetDesign__Composition__Provider=OpenAI

fly secrets set --app $APP \
  BouquetDesign__Bfl__ApiKey='<bfl key>' \
  BouquetDesign__Preview__Provider=Bfl

# Pilot controls (non-secret; may also live in [env] of fly.toml)
fly secrets set --app $APP \
  BouquetDesign__PilotVendorIds__0='<vendor guid>' \
  BouquetDesign__Limits__GlobalMonthlyUsdCap=100

Every fly secrets set restarts the machine; batch them. Add the new keys to SECRETS-AND-ENV-VARS.md when you set them.

BouquetDesign__PreviewsEnabled Previews only true
BouquetDesign__PilotVendorIds__N Allow-list (empty = everyone) empty

BouquetDesign__{…}__EstimatedUsd Max $ reserved per call 0.010 / 0.005 / 0.020
BouquetDesign__Limits__* RecognitionsPerMonth 20, CompositionsPerMonth 20, PreviewsPerMonth 40, MaxActivePreviewsPerVendor 2, GlobalMonthlyUsdCap 100

Model ids are configuration, not code. Before switching a provider on, confirm the id is current (gpt-4.1-mini was the plan’s priced baseline; GPT Image models are named like gpt-image-1/gpt-image-2). If you use GPT Image for previews set BouquetDesign__Preview__Model and __EstimatedUsd=0.075.

3. Image generation model

3.1 Recommended now: hosted FLUX.2 [klein] 4B via the BFL API (no deployment)

Nothing to host. The Bfl adapter submits POST {BaseUrl}/flux-2-klein-4b with the recipe prompt and up to MaxReferenceImages (default 2, klein accepts 4) resized stock photos, persists the returned polling_url as the job’s provider task id, polls it until Ready, and copies the result (BFL result URLs expire within minutes) into the private bucket. Because the task id is stored, a worker crash or redeploy resumes polling instead of paying for a second render.

  1. Create an account on bfl.ai, buy credits (1 credit = $0.01; ~$10 is plenty for the pilot) and create an API key.
  2. fly secrets set BouquetDesign__Bfl__ApiKey=… BouquetDesign__Preview__Provider=Bfl.
  3. Check the request/response field names once against BFL’s current API reference (https://docs.bfl.ai, OpenAPI at https://api.bfl.ai/openapi.json). The adapter was written to the documented shape (prompt, input_image, input_image_2…, width, height, output_format; response id, polling_url; poll status Ready|Pending|…, result.sample) and is covered by mock-HTTP tests only — this build environment could not reach BFL.
  4. Generate one preview from the app on a test vendor and check fly logs for BFL returned … warnings.

Price: ≈ $0.014 per 1 MP text-to-image, slightly more with reference images → budgeted at $0.020.

3.2 Alternative: OpenAI GPT Image

BouquetDesign__Preview__Provider=OpenAI, model via BouquetDesign__Preview__Model, size BouquetDesign__OpenAI__ImageSize (1024x1024), quality …__ImageQuality (medium). Synchronous — there is no recovery handle, so a response lost mid-flight is recorded as OutcomeUnknown and never re-sent automatically. Medium quality ≈ $0.053 output + input → budgeted at $0.075.

3.3 Optional experiment: self-hosting FLUX.2 [klein] 4B on a serverless GPU

Only worth it once there is measured demand (break-even analysis in the cost report: thousands of previews/month). Fly has no GPUs, so this lives outside Fly; keep the API on Fly.

  1. Platform: Runpod Serverless (or Modal/Replicate) with a 24 GB GPU (A5000/4090/L4 class). klein 4B needs ~13 GB VRAM. Use the 4B weights — Apache-2.0; the 9B variant has a different licence.
  2. Container: Python 3.11, torch + CUDA, diffusers (version with FLUX.2 klein support — pin it), weights black-forest-labs/FLUX.2-klein-4B baked into the image or on a network volume (avoids a multi-GB download per cold start). Handler: accept {prompt, images[base64], width, height, seed}, run the pipeline (≈ 4 steps for klein), return a JPEG base64.
  3. Endpoint security: Runpod endpoint API key as a Fly secret; never expose the endpoint publicly.
  4. App integration: add a SelfHosted IPreviewRenderer (≈ 1–2 days; follow-up) that calls the endpoint’s async run + status API and stores the job id as ProviderTaskId, exactly like the BFL adapter, so crash recovery keeps working. No mobile change.
  5. Measure before switching: cold-start seconds, warm seconds per image, billed seconds per accepted preview. At $0.69/h serverless: 10 billed s ≈ $0.002/image, 60 s ≈ $0.012/image. Idle-scaling to zero is mandatory — an always-on A5000 is ≈ $197/month.

4. Expected costs

AI usage is bounded by the in-app limits (per vendor per month: 20 recognitions, 20 recipe sets, 40 previews; global cap $100). Planning allowances (from the cost report): recognition + composition ≈ $0.015/session, economy preview (klein) $0.020, quality preview (GPT Image medium) $0.075, +20 % buffer.

Phase Fixed infra delta AI usage Monthly total
Prototype testing now (free providers) ≈ $5–7 (API always on) + R2 $0 $0 ≈ $5–7
Provider evaluation (one-off, 2–4 days) — $25–50 one-off (≈ 300 klein + 300 GPT previews + 50 sessions) —
Pilot, 10 shops, 20 sessions × 2 previews each ≈ $5–7 $13 (klein) – $40 (GPT medium) ≈ $20–50
50 shops ≈ $10–15 (consider separate worker) $66 – $198 ≈ $80–215
100 shops ≈ $15–25 $132 – $396 ≈ $150–420

Hard ceiling: the worst a single vendor can cost per month is 20 × $0.010 + 20 × $0.005 + 40 × $0.020 = $1.10 (klein) or 40 × $0.075 + $0.30 = $3.30 (GPT) before the 20 % buffer; the global cap ($100) stops all new paid work platform-wide. Set a provider-side budget alert too (OpenAI usage limit, BFL credit balance) — the app’s cap is the primary gate, the dashboards are a backstop.

5. Testing and validation flow

5.1 Automated tests (every change)

# Backend
dotnet test tests/FlowerShop.Domain.Tests --filter FullyQualifiedName~BouquetDesign   # 31 domain tests
dotnet test tests/FlowerShop.Tests.Unit   --filter FullyQualifiedName~BouquetDesign   # 32 flow + provider tests
# Mobile (sibling repo)
dotnet test tests/FlowerShop.VendorEmployee.Tests/ -p:TestsOnly=true --filter FullyQualifiedName~BouquetDesign

Covered: stock validation (duplicate lines, unknown ids, stem bounds), cost maths (64.00 PLN / 46.67 %, incomplete costs, labor+overhead 92.40, rounding), state machine, idempotent replays and 409 on changed payloads, cross-tenant 404s, quotas / $ cap / kill switch, preview caching and double-tap, crash recovery (unsubmitted → retried; submitted → OutcomeUnknown, never resent), stale stock discard, deletion, image processing, BFL/OpenAI adapters on mock HTTP.

5.2 Local end-to-end (free providers, no keys)

docker-compose -f docker/docker-compose.dev.yml up -d postgres      # or any local PostgreSQL 15+
cd src/backend/FlowerShop.API
ASPNETCORE_ENVIRONMENT=Development Authentication__UseKeycloak=false ConnectionStrings__Redis= \
  dotnet run --no-launch-profile --urls http://localhost:8080

TOKEN=$(curl -s -X POST localhost:8080/api/v1/auth/dev-token -H 'Content-Type: application/json' \
  -d '{"username":"v@x.pl","vendorId":"11111111-1111-1111-1111-111111111111","vendorType":"TraditionalShop","role":"VendorAdmin"}' | jq -r .token)
H="Authorization: Bearer $TOKEN"
S=$(curl -s -X POST localhost:8080/api/v1/vendor/design-sessions -H "$H" -H 'Content-Type: application/json' -d '{"inputMode":"Photos"}')
SID=$(jq -r .id <<<"$S")
curl -s -X POST localhost:8080/api/v1/vendor/design-sessions/$SID/photos -H "$H" -F photo=@stock.jpg -F clientPhotoId=p1 | jq '.version,.photos'
curl -s -X POST localhost:8080/api/v1/vendor/design-sessions/$SID/recognize -H "$H" -H 'Idempotency-Key: r1' \
  -H 'Content-Type: application/json' -d '{"expectedVersion":2}' | jq .state            # Recognizing
sleep 3; curl -s localhost:8080/api/v1/vendor/design-sessions/$SID -H "$H" | jq '.state,.inventory'
# … PUT /inventory (confirmed:true, add unitPrice), POST /recipes (Idempotency-Key), poll,
#     POST /recipes/{rid}/preview, poll, GET preview/content > preview.jpg

The mobile app’s Debug build talks to http://10.0.2.2:8080 from the Android emulator, so the same local API serves the app.

What was verified this way on 2026-10-14 against PostgreSQL 16: migration applied; create (201) → photo upload re-encoded to 1600 px → recognize (202, 400 without Idempotency-Key) → estimates → stale expectedVersion 409 → confirm → cost ceiling with a missing price 422 → compose (202) → 3 recipes with incomplete cost and no margin → preview (202) → Ready, JPEG bytes → save → saved list → cost profile GET/PUT → usage counters → delete (204) → 404; another vendor got 404 for session and photo bytes.

5.3 Production smoke (after deploy, free providers)

  1. GET https://api.findmyflowers.pl/health/ready → 200; logs show Design job worker started.
  2. Log into a Release build of the vendor app (it targets api.findmyflowers.pl) as a test vendor.
  3. Home → AI Florist → take 1–2 photos → Review stock: estimates appear with the “Counts are estimates” banner (Fake recogniser = roses / lisianthus / eucalyptus / wrap / ribbon).
  4. Edit a count, add prices for some lines, Confirm stock → Create 3 recipes → three recipes appear within ~5 s. One missing price ⇒ “Known cost … · 1 price missing”, no margin.
  5. Generate preview on one recipe → placeholder image labelled “AI inspiration” within ~5 s.
  6. Save, open Saved recipes, Share (text). Kill and reopen the app mid-composition — it resumes.
  7. Check the database:
SELECT "Kind", "State", count(*), sum(coalesce("ActualUsd","ReservedUsd")) AS usd
FROM "DesignJobs" WHERE "CreatedAt" >= date_trunc('month', now()) GROUP BY 1,2;
-- stuck work (should be empty)
SELECT "Id","Kind","State","LeaseExpiresAt" FROM "DesignJobs"
WHERE ("State"='Queued' AND "CreatedAt" < now() - interval '5 minutes')
   OR ("State"='Running' AND "LeaseExpiresAt" < now() - interval '2 minutes');
  1. Confirm the R2 objects exist under design/{vendorId}/… in flowershop-design-private and that the bucket has no public URL.

5.4 Provider evaluation (plan Task 0 — before enabling paid providers for real vendors)

  1. Collect 30–50 consented stock photos from 2–3 shops (overlapping angles, similar species, poor light). Keep them out of Git; record ground truth (species, colour, count range).
  2. Restrict to a test vendor: BouquetDesign__PilotVendorIds__0=<test vendor>. (The allow-list applies to everyone, so other vendors are locked out of new work during the evaluation.)
  3. Run each photo set with Recognition=OpenAI; count corrected lines per session.
  4. For the same confirmed stock run Composition=OpenAI and the Deterministic composer; florists rate usefulness blind.
  5. Render the same recipes with Preview=Bfl (klein) and Preview=OpenAI (GPT Image medium); florists rate unsupported species, wrong colours, invented materials, usefulness; count re-renders.
  6. Record per call in docs/verification/ai-bouquet-assistant/evaluation-results.csv (mobile repo): sample_id,step,provider,model,prompt_version,reference_count,latency_ms,input_tokens,output_tokens,billed_usd,inventory_lines,corrected_lines,recipe_valid,florist_useful,rerender_count,error_code. Latency/state per job is in DesignJobs (LatencyMs, Provider, Model, PromptVersion).
  7. Gates: 100 % of persisted recipes stock-valid (guaranteed by code); < 30 % of lines corrected; median session-to-recipes < 45 s; preview p95 < 90 s; ≥ 70 % rated useful; economy session ≤ $0.10 with two previews. Choose the provider with the lowest cost per accepted preview. If no renderer passes, ship recipes with BouquetDesign__PreviewsEnabled=false.

5.6 Monitoring during the pilot

  • fly logs | grep -E "Design job|BFL returned|OpenAI returned" — failures, provider status codes.
  • Weekly: the spend query in §5.3 vs. the provider invoices; replace the EstimatedUsd allowances with measured p95 costs.
  • Alert (manual for now, follow-up T-28-021): any OutcomeUnknown, jobs queued > 5 min, monthly spend

    80 % of the cap.

6. Rollback

  • Stop paid work: fly secrets set BouquetDesign__Enabled=false (or PreviewsEnabled=false). Existing sessions and saved recipes stay readable.
  • Revert to free providers: unset the *__Provider secrets.
  • Code rollback: redeploy the previous image. The three new tables are unused by older code and can stay; do not drop them (saved recipes live there).
  • Return to scale-to-zero: revert §2.1 only after the worker moved to its own machine (§2.2).
